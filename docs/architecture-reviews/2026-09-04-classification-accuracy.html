Live defect — found during exploration

Every human decision silently erases the LLM judge's verdict

_reroute() (classification/endpoints.py:82-108) copies 20 of RoutingInput's 22 fields. The two it omits are judge_final_label and judge_reasoning. Both have pydantic defaults of None, so nothing raises — and routing.py:95-96 assigns them unconditionally. The judge's verdict and its reasoning are overwritten with NULL on every human decision.

23

records judged by the LLM

12

still hold judge_final_label

11

judged and overridden — reasoning gone

The arithmetic closes exactly: 23 judged − 11 overridden = 12 surviving. Note judged_by_llm is copied, so these records still claim the judge ran while carrying no trace of what it said — the worst of both states for an audit trail. This is not a hypothetical. It is the failure mode Candidate 1 exists to make impossible, and it is why that candidate is rated Strong rather than Worth exploring.

Candidate 1

Routing should expose an operation, not a 22-field struct

Strong

Files

  • classification/domain/results.py:19-45 (22 fields)
  • classification/nodes/routing.py:70-110
  • classification/coordinator.py:152-178 (construction #1)
  • api/routes/classification/endpoints.py:82-108 (construction #2)

Problem

RoutingNode is a shallow module: its interface (22 fields a caller must supply) is larger than its implementation (a subdirectory if, a storage call, 25 lines of field assignment). The human-decision endpoint has an opinion about three of those fields and must correctly restate the other nineteen.

Forgotten — 2 fields

judge_final_label judge_reasoning

Nulled on every decision. 11 records already damaged.

Solution

Give RoutingNode two named operations for the human paths — apply_human_decision(job_id, label) and reopen_for_review(job_id) — each loading the record and mutating only the fields that path owns. RoutingInput stays as the machine pass's interface, where all 22 fields are genuinely new information.

Pass-through stops being something a caller performs and becomes something the module does by not touching. The 2-field omission becomes unrepresentable.

Benefits

  • Locality: adding a 23rd signal is a 2-file edit (model + machine pass), not 5. Today, forgetting one of the five silently zeroes the field on the next human decision.
  • Leverage: the endpoint learns 2 verbs instead of 22 field names, and _reroute's 26 lines disappear.
  • Tests: test_classification.py:136-144 currently hand-mutates 4 fields to fabricate a decided record — reaching past the interface because no operation for "decide" exists. With one, the setup becomes a single call, and the decision→reopen sequence gains coverage it has never had.

Deletion test: delete the pass-through half of RoutingInput and the "restate 19 fields correctly" burden reappears in two call sites — but the judge-field bug does not, because there is nothing left to forget. Complexity concentrates. Earns its keep.

Candidate 2

One invariant, three enforcement mechanisms, fifteen sites

Strong

Files

  • classification/nodes/routing.py:97-109
  • api/routes/classification/endpoints.py:69-70, 102-107
  • database/models.py:195-205 (comments only)
  • services/metrics/service.py:28-46 (reader)
  • + 11 more sites

Problem

"original_label, expected_label and machine_review_route are write-once" is enforced three incompatible ways in a single 13-line function — and for one of the three, not at all. Nothing in the type system or the schema stops a sixteenth site from writing them.

Three fields, three different guard polarities — routing.py:97-109:

record.original_label = routing_input.original_label          ← no guard at all

if routing_input.expected_label is not None:                  ← guard on the INPUT
    record.expected_label = routing_input.expected_label

if record.machine_review_route is None:                       ← guard on the RECORD
    record.machine_review_route = (...)

original_label's write-once-ness is not enforced here at all — it is delegated upward to whoever calls the node, which is exactly why Candidate 3's flag argument had to be invented, and why it produced a bug during this feature's own implementation.

Before — the rule is a convention

routing.py — 2 guards, opposite polarity
endpoints.py — a ternary + a flag param
models.py — a comment
results.py — another comment
metrics/service.py — must re-derive it to read
0015 migration — infers it a 3rd way
tests — one asserts it, one bypasses it

15 sites. Adding a 16th costs nothing and breaks silently.

After — the rule is the interface

_save_record — one polarity:
"set if currently NULL"
everything else — cannot reach the fields

The endpoint's ternary, the flag param, and the test helper's or review_route fallback all disappear.

Solution

Move all three guards into _save_record with one consistent polarity — set when the record's field is currently NULL, never otherwise. This is already how machine_review_route works; the change is making the other two match. Callers then cannot fabricate history whatever they pass.

Benefits

  • Locality: one function to read, one to test, one to fix. Today a reader must hold five files in their head — _score() in the metrics module needs exactly this knowledge and re-derives it.
  • Leverage: the accuracy figures depend on these three fields being trustworthy. Every site that can write them is a site that can corrupt a metric — and two already did this session.
  • Tests: the guards become testable in isolation instead of only through a full route→decide→reopen sequence.

Note: CLAUDE.md documents this invariant in prose (the "Immutable classification history" section added this session). That is the correct stopgap — but a convention that needs documenting in a second file is a convention the code should be enforcing.

Candidate 3

The capture_prediction flag argument

Worth exploring

Files

  • endpoints.py:70 (param)
  • endpoints.py:103-105 (use)
  • endpoints.py:153 (True — decision)
  • endpoints.py:211 (False — reopen)

Problem

A boolean parameter selecting between two behaviours inside a shared helper — and its False branch is a no-op (original_label=record.original_label is what plain pass-through already does). One live branch, one dead one, and a 6-line docstring explaining a boolean.

This flag already caused a bug — during its own implementation. The first version of _reroute had no flag: reopening a legacy record wrote the reviewer's label into original_label, fabricating a machine prediction that never happened. A failing test caught it. The flag is the patch, and it works — but it places the decision-vs-reopen seam inside a shared helper, when the two endpoints already differ in their guard, their exception, their audit event, and their label source. There is a second, correlated flag beside it: human_overridden — and the signature permits the meaningless combination capture_prediction=True, human_overridden=False.

Solution

Subsumed by Candidates 1 and 2. If write-once is enforced record-side (C2), the flag has nothing left to protect and deletes itself. If routing exposes two named operations (C1), the two call sites stop sharing a helper at all. Standalone, the fix is to split _reroute in two — but that duplicates the pass-through block rather than removing it.

Benefits

  • Locality: "which operation am I in" stops being a parameter threaded through a helper.
  • Leverage: two correlated booleans collapse into the choice of which method you call.
  • Why not Strong: the current code is correct and tested. This is a shape problem, not a defect — and doing C1 or C2 removes it for free.

Candidate 4

Four parallel field lists for one concept

Speculative

Files

  • database/models.py:164-208 (ClassificationRecord)
  • classification/domain/results.py:19-45 (RoutingInput)
  • classification/domain/state.py:14-45 (ClassificationState)
  • classification/domain/state.py:48-81 (ClassificationUpdate)

Problem

Four declarations of roughly the same ~18 fields, edited together on every change. coordinator.py:29 (_dump) exists solely to bridge two of them. This is the structural reason a new signal costs five files.

Solution

No clean one. The four serve genuinely different roles — ORM row, LangGraph state, LangGraph partial update, node input — and LangGraph's TypedDict state contract resists sharing a base with a pydantic model or a SQLAlchemy row. A shared ClassificationSignals value object nested inside each is conceivable but would touch every node.

Benefits

  • Locality: a new signal would be one edit instead of four.
  • Why speculative: the blast radius is every classification node, the framework fights it, and Candidate 1 removes most of the pain without touching the structure. Listed so a future review knows it was considered and priced.

Acknowledged, correctly priced

The frozen prefix table

ground_truth.py:18-37 and 0015:22-39 hold the same map. The migration copy is correctly frozen. Missing: a back-reference from the live table to the frozen one, so the copy is discoverable. One comment.

list_all()'s hidden ceiling

classification_record.py:10 loads every record into memory for the accuracy report. Fine at 70 records; the interface makes the unbounded fetch invisible. Wants a ponytail: comment naming the ceiling, not a fix.

expected_label wrapper

ground_truth.py:61-68 — 8 lines, 6 of them docstring, one caller. Deletion test says moves, not concentrates. The enum round-trip earns its keep in tests. Leave it.

Top recommendation

Fix the judge-field loss first, then take Candidate 2

The defect is not a refactor

Two missing lines in _reroute stop the bleeding today. The 11 damaged records cannot be recovered — the judge's reasoning is gone. Do this before any structural work, and independently of it.

C2 is the cheapest structural win

Moving three guards into _save_record touches one function, deletes the flag argument (C3) for free, and makes the class of bug that produced both this session's history defects unrepresentable.

C1 is the real fix, and it's bigger

Only C1 makes the judge-field omission impossible rather than merely fixed. But it changes RoutingNode's interface and touches the coordinator. Worth doing — after C2, not instead of it.

Sequence: the 2-line defect fix (+ a regression test asserting judge fields survive a decision) → Candidate 2, which absorbs Candidate 3 → Candidate 1 when the next signal needs adding, since that is when its cost becomes visible. Candidate 4 stays parked.

One caveat on scoring: the judge fields are not read by MetricsService, so the published accuracy figures are unaffected by this defect. The loss is to the audit trail and to any future analysis of judge agreement.
