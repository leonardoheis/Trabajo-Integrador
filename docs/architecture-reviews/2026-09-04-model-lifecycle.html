Candidate 1

A GPU residency module behind one seam

Strong

Files

  • model_cache.py (19 lines)
  • knowledge/llm/llama.py
  • ingesta/llm_provider.py
  • classification/nodes/second_opinion.py
  • ingesta/nodes/node4_duplicate_control.py
  • knowledge/embeddings/embedder.py
  • + 4 call-site modules

Problem

There are five unloader functions in five modules, each imported individually by whoever needs them. services/pipeline/service.py imports all five; auth/endpoints.py imports five; knowledge/endpoints.py imports two. Every caller must know which models exist, which are safe to evict, and what guard to check first — knowledge that should live in one place.

Three live defects this shape produces — each one a symptom of the guard being a convention rather than part of an interface:

  1. Four of five unloaders have no busy guard. Only unload_chat_llm() checks. The rest evict unconditionally.
  2. TOCTOU race in the one guard that exists. is_chat_llm_busy() takes the lock, releases it, then evict_lru_cache() runs unlocked — a generation can begin in that window. unload_chat_llm never holds _generation_lock.
  3. Four call sites, four different guard policies. pipeline_warmup suppresses on busy-pipeline; auth_logout uses busy-pipeline to gate a different set; _release_gpu_models checks nothing; llm_judge.py:80 unloads mid-node with no guard at all.

Solution

One module owning GPU residency. Its interface is intent-shaped, not mechanism-shaped: reserve_for_chat(), reserve_for_pipeline(), release_all().

Which five models exist, which are pipeline-owned, and which are busy becomes implementation. model_cache.py already exists as a seam but sits one level too low — it knows how to evict a cache, not which caches there are or when eviction is safe.

Benefits

  • Locality: adding a sixth model touches one module, not five call sites. The busy-guard bug gets fixed once.
  • Leverage: callers learn three verbs instead of five functions plus two guard predicates.
  • Tests: today they monkeypatch Llama and call get_chat_llm.cache_clear() by hand in a try/finally, repeated per test with no fixture. Through this interface, an in-memory adapter records reserve/release calls — no CUDA, no lru_cache poking.
  • Also fixes: _release_gpu_models() runs 5×(gc.collect() + empty_cache()) synchronously on the event loop, twice per job — while auth_logout correctly wraps the same calls in asyncio.to_thread. One module makes that decision once.

Deletion test: delete this module and the five-model list, the pipeline-vs-chat ownership rule, and the busy-check discipline all reappear in four route modules. Complexity concentrates — it earns its keep.

Candidate 2

The duplicated in-flight counter

Strong

Files

  • knowledge/llm/llama.py (_ActiveGenerations)
  • services/pipeline/service.py (_JobsInFlight)

Problem

Two modules implement the same "mutable box around a count" pattern — with near-identical docstrings explaining the same PLW0603 workaround. They have diverged: _ActiveGenerations has a lock and underflow detection, _JobsInFlight has neither, despite being mutated from background tasks.

Before — diverged twins

Same pattern, same rationale, different safety.

After — one adapter, two instances

InFlightCounter
lock ✓ · underflow log ✓
generations
jobs

Two adapters ⇒ the seam is real, not hypothetical.

Solution

One InFlightCounter module with a context-manager interface (generation_in_flight() already has this shape). Two instances replace the two hand-rolled boxes. Thread-safety and underflow detection become properties of the type, not of whoever wrote it that day.

Benefits

  • Locality: the "counter leaked ⇒ unload silently no-ops" failure mode gets one place to be fixed and tested.
  • Leverage: a third counter (indexing? OCR?) costs one line.
  • Tests: counter semantics test once, directly — currently only reachable through a full streaming test with a mocked Llama.

Candidate 3

The three-layer aclosing chain

Worth exploring

Files

  • api/routes/knowledge/endpoints.py:102
  • knowledge/chat/service.py:55
  • knowledge/memory/service.py:53
  • knowledge/llm/llama.py (astream)

Problem

Correct cleanup requires every layer to wrap the one below in contextlib.aclosing. Miss one and the counter leaks silently — which is precisely what happened twice this session. The requirement is real but invisible: nothing in any interface says "you must close me".

The fragile chain

sequenceDiagram participant C as Client participant E as _stream() participant S as ChatService.astream participant L as LlamaCppChatLlm.astream participant T as producer thread C->>E: disconnect Note over E: aclosing ✓ (layer 1) E->>S: GeneratorExit Note over S: aclosing ✓ (layer 2) S->>L: GeneratorExit Note over L: finally → stop.set() L->>T: stop event Note over T: releases counter

Solution

Two options, materially different in cost:

(a) Cheap: a test that asserts the invariant end-to-end — abandon at each layer, assert the counter released. Makes the requirement enforced rather than documented.

(b) Deeper: collapse the chain. If ChatService returned a single closable stream object rather than a nested generator, there would be one layer to close instead of three.

Benefits

  • Locality: option (b) makes it impossible to add a fourth layer that forgets to close.
  • Tests: the abandonment case is currently tested only at the llama layer — the two upper layers have no coverage for it.
  • Caveat: option (b) is a real redesign of the streaming interface. Start with (a).

Candidate 4

Settings read at call time

Speculative

Files

  • knowledge/llm/llama.py:95,121,122,136,137,177,178
  • knowledge/retrieval/retriever.py:40
  • api/routes/knowledge/endpoints.py:140

Problem

LlamaCppChatLlm takes config in its constructor but then reads Settings.slm_temperature and Settings.slm_top_p directly at generation time. Half the configuration is injected, half is ambient — so a test that constructs the object still can't fully control it.

Solution

Move the remaining Settings reads into __init__, matching the pattern the same class already uses for model_path and n_ctx. Consistency, not a new abstraction.

Benefits

  • Tests: sampling params become settable without monkeypatching a global.
  • Why speculative: no bug has come from this, and nothing currently varies these per-instance. One adapter ⇒ hypothetical seam.
